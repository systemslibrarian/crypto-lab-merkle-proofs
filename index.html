Merkle Proofs

Inclusion & Consistency · SHA-256 · RFC 6962

Build a Merkle tree, then generate and verify inclusion and consistency proofs against its root using RFC 6962 domain separation.

WHY IT MATTERS

One tiny root commits to millions of records, and a handful of hashes proves any one is in the set — without the whole set. This is how Bitcoin light clients, Git, and Certificate Transparency stay honest at scale.

Where this sits: this lab is about what a proof means — where the trusted root has to come from, the exact bytes hashed at every step, RFC 9162 index-based verification, the attacks a construction survives or does not, and a real Certificate Transparency entry checked against a production log. If you want the structure instead — the tree drawn with parent-to-child connectors, one climb walked level by level with the nodes lighting up as the running hash rises, and the recomputed and committed roots asserted equal byte for byte at the top — that is crypto-lab-merkle-vault. The two labs share a subject and deliberately answer different questions about it.

What you'll be able to do

  • Generate and verify an inclusion proof by hand — and say why it's only ⌈log₂ n⌉ hashes.
  • Explain where the trusted root must come from, and why a proof without that is worthless.
  • Break two real constructions: the second-preimage forgery (no domain separation) and CVE-2012-2459 (odd-node duplication).
  • Verify a consistency proof and state exactly what "append-only" does and doesn't guarantee.

1 · What is a Merkle Tree?

A Merkle tree is a binary tree of hashes. Each leaf holds the hash of one data block; each internal node holds the hash of its two children concatenated. The single hash at the top — the root — commits to every leaf at once: change any byte of any block and the root changes.

This demo uses real SHA-256 via the browser's WebCrypto API, with RFC 6962 domain separation:

  • leaf hash = SHA-256(0x00 ∥ data)
  • node hash = SHA-256(0x01 ∥ left ∥ right)

4 · Verify a Proof

A verifier recomputes the root from only the leaf and the proof, then checks it against the trusted root. Try tampering — the verdict flips to REJECTED the moment anything changes.

Walk it:
Predict

You flip one bit of a single sibling hash deep in the proof. Will verification still pass?

No. That bit changes the parent hash, which changes its parent, all the way up — the recomputed root no longer matches. One bit anywhere in the leaf or proof is enough to break it. This is the avalanche property of SHA-256 plus the tree's hash chaining.

Where does the trusted root come from?

Everything above assumed the verifier already holds the right root. That assumption is the entire security model. A proof only ties a leaf to some root — if the person making the claim also hands you the root, they can build a tree around any lie.

Predict

Mallory invents a fake transaction, builds her own Merkle tree around it, and sends you the leaf, the proof, and the root. Does verification pass?

Yes — perfectly. The hashes are all real SHA-256 and all self-consistent. Verification can never tell you the root is the agreed-upon one; only the channel that delivered the root can. That's why Bitcoin roots live in mined block headers and CT roots come as signed tree heads that clients gossip and compare.

6 · Security: Why the 0x00 / 0x01 Prefixes Matter

Without domain separation, a leaf is hashed exactly like an internal node — so an attacker can take an internal node's two child hashes, glue them into a 64-byte "leaf", and prove inclusion of a leaf that never existed. This is the classic second-preimage (leaf-node confusion) attack. RFC 6962's 0x00/0x01 prefixes put leaf and node hashes in separate spaces and shut it down.

Turn the toggle off to see the forgery accepted (vulnerable), then back on to see it rejected. The main builder above always keeps domain separation on.

A second pitfall: odd-node handling (CVE-2012-2459)

When a level has an odd number of nodes, something must be done with the lone node. Bitcoin duplicated it (hash(x ∥ x)), which let an attacker pad a block's transaction list with a repeated last transaction to get the same Merkle root — mutating blocks and splitting the network. RFC 6962 promotes the lone node unchanged, which has no such collision.

7 · Consistency (Append-Only) Proofs

Everything above proves inclusion — that one leaf is in the tree. A consistency proof answers a different question that logs care about: is the old tree of size m an exact prefix of the new tree of size n — i.e. did the log only append, never rewrite history? This is the guarantee Certificate Transparency is built on.

Why it works: the old root is stitched together from a few complete subtrees — and those exact subtrees still sit, byte-for-byte, inside the new tree. The proof hands the auditor just enough subtree roots to rebuild both the remembered old root and the claimed new root. If the same handful of hashes can reproduce both, nothing before entry m changed.

The log (a growing list of certificates; shaded = the old size-m prefix):

  • the old size-m tree (shaded prefix)
  • ◆ proof hash inside the prefix — rebuilds the old root, then reused for the new one
  • ◇ proof hash in the appended region — completes the new root
Predict

The log operator deletes one early entry but keeps appending, so the log is still growing. Will the consistency proof still verify?

No. "Append-only" means every old entry must stay at its exact position. A deletion shifts every later leaf one slot left, which changes every subtree containing them — the remembered old root can no longer be rebuilt from the new tree's subtrees. Same for reordering: same contents, different positions, different hashes. Try both below.

Every attack keeps the auditor's remembered old root but alters the log the operator presents — the consistency proof then fails, exposing the tampering. Honest limit: tampering is only caught if it touches entries the old root committed to (positions < m) — a change entirely after position m is invisible to this old root, which is why auditors keep requesting fresh signed tree heads.

9 · Where Merkle Proofs Are Used

Bitcoin & Ethereum

Block headers commit to a Merkle root of all transactions. An SPV / light client proves a transaction is in a block with a short branch — no need to download the full chain. Caveat if you try this at home: Bitcoin's construction differs from this lab's — double SHA-256, byte-reversed txids, no domain separation (hence section 6's CVE), so its roots won't match an RFC 6962 tree.

Git

Every commit, tree, and blob is content-addressed by hash, forming a Merkle DAG. The commit hash pins the entire history; any tampering changes every descendant hash.

Certificate Transparency

CT logs (RFC 6962 — the exact construction here) publish a Merkle root so anyone can prove a certificate was logged and that the log is append-only. Section 8 verifies a real entry from a live log.

Stateless / light clients

Merkle (and Verkle) proofs let a client check that an account balance or state value is part of a committed root without holding the whole state tree.
